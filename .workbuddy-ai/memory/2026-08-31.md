## 讲解 Codex harness 并与本项目对比（用户提问）

### 关键概念澄清（重要，避免后续混淆）

**「harness」在本项目与 Codex 中含义不同，别混用：**
- Codex harness = **执行外骨骼/运行时**：agent loop + sandbox + approval + thread-store
- 本项目 `src/water_agent/harness/` = **评测跑分器**：读 JSONL → 执行 → 判分 → 报告 → CI 退出码

真正对标 Codex harness 的是本项目**尚未建设的服务化执行层**，不是 harness/ 目录。

### Codex harness 要点（2026-08-19 官方宣布开源，Apache-2.0）

- 三层接口：`codex exec`（CI/一次性）→ Codex SDK（程序化编排）→ app-server（持久会话，JSON-RPC 2.0）
- 三原语：**Thread**（会话，可 fork/resume/archive）/ **Turn**（一轮请求+工作）/ **Item**（原子输入输出单元）
- 事件分两类：
  - **notification（无 id）**：`item/started` / `item/completed` / `item/agentMessage/delta` / `outputDelta`
  - **server request（有 id，必须回复）**：`item/permissions/requestApproval` / `mcpServer/elicitation/request`
  - 「告知」与「请示」在协议层分离 —— 值得抄
- 策略由宿主注入：`turn/start` 时传 `sandboxPolicy`（workspaceWrite 等）+ `approvalPolicy`
- 官方数据：ARC-AGI-3 上靠 retained reasoning + context compaction，同模型 13.3% → 38.3%，输出 token 降 6 倍

### 对比结论

相似：有界循环守卫（本项目 MAX_TOTAL_STEPS=10 等双上限）、事件化可观测（trace 事件粒度与 Item 事件接近）、中断/恢复意图（LangGraph checkpointing + interrupt ≈ turn/interrupt + thread/resume）

差异：本项目只读检索+生成，无危险操作 → **当前没有沙箱/审批层是合理的**，不是缺陷；
`citation_check`（引用必须来自当次 context）是领域红线，通用 harness 不提供，必须自建

## 「做成 DSH 那样的垂直产品」架构咨询

用户问：如何把给排水 agent 做成 DSH（DeepSeek Harness）那样的形态，但作为给排水垂直落地产品，该改什么、取舍什么。

### DSH 事实（2026-08-13 开源 v0.1 DP，CLI 叫 `dsh`）

- 元框架 **Cordis**（源自 Koishi 聊天机器人框架），核心论文《A Programming Paradigm for Spatiotemporal Composability》（DeepSeek-AI + 北大）
- **一切皆插件**：不仅 Skill/MCP，连 Model Adapter / Tool Registry / Session Log / Agent Loop / Web UI 都可热插拔
- 两个机制：**Revertible Effects**（`ctx.effect` 注册时留 inverse，卸载时逆序撤销）、**Reactive Coeffects**（声明依赖，Provider 变化时 activating/deactivating/neutral）
- 目标：Self-Evolving Agent Harness（Agent 可改自己的 Runtime）
- 生态：GitHub `dsh-plugin` 标签一周数千插件；代表插件 Agent Teams（Captain+成员）、dsh-genui（对话内渲染卡片图表）、dsh-context（上下文可视化）、dsh-browser（操控真实 Chrome）
- 已知代价：Cordis 论文自承认集成组件可能 **O(n²)** 增长；社区实况插件不兼容致 Web 起不来；DeepSeek V4 API 涨价（高峰 3–4.5 倍）；争议为「需自行组装的半成品」

### 本项目采纳结论（已给用户）

**核心判断：不照抄「一切皆插件」。** DSH 插件化的目的是 self-evolving，而让 Agent 自我修改检索/引用逻辑直接撞「引用可追溯」红线 → 反需求。

目标三层架构：
- **应用层（垂直护城河）**：意图路由 / 卡片渲染器 / 人工确认 gate
- **能力层（唯一插件化处）**：Calculator 注册表 / Retriever 注册表 / Exporter 注册表
- **运行时（保持薄，不插件化）**：LangGraph graph + checkpoint/trace + 撤销栈
- **红线**：citation_check 内置于运行时，不可替换、不可被 Agent 自改

**抄 2 个机制**：
1. Revertible Effects → Python 里做 `EffectStack` context manager（无需引 Cordis）。用于 P2 文档生成、P4 CAD 写操作
2. Reactive Coeffects → 计算工具声明依赖的公式口径 Provider（正好落地 ADR-01）；corpus 变更时检索组件自动感知（GB50015 现仅 4.7KB、221 个 md 未入库，将来补齐需触发重建索引+重跑基线）

**抄 1 个产品思路**：生成式 UI（对标 dsh-genui），但**做成内置一等公民而非插件**——计算卡片/引用卡片是高频刚需，不是可选装饰

**4 个不抄**：插件化 agent loop / 建插件市场生态 / self-evolving / 现在做多 Agent（单 Agent 基线还没跑出来）

**最大取舍：不换底座。** DSH 是 TS/Cordis、Codex 是 Rust+TS，而本项目水力计算·材料统计·Excel 导出强依赖 Python 生态 → 执行层继续 LangGraph(Python)，仅把事件模型向「notification vs server request 分离」靠拢

### 落地时点

A（现在跑基线，不动架构）→ B 建 hydraulics 时按 Calculator 注册表接口写 → C 语料扩容时落 Retriever 注册表 + 依赖声明 → P2 落撤销栈 + 人工确认 gate → P5 落卡片渲染器（内置）

### 可借鉴时点（对应路线图，承上节 Codex 对比）

- **P2**（Human-in-the-loop，ADR-04 生成正式文档前确认）→ 抄「server request 必须回复」模式，别用软约定
- **P4**（接 CAD/BIM，有写操作）→ 抄 sandboxPolicy/approvalPolicy「策略由宿主注入」设计，现在可预留接口
- **P5**（前端流式）→ 抄 Item 三件套 started/completed/delta，本项目 trace 缺「流式增量」层
- context compaction 暂不急（当前单轮问答为主）
