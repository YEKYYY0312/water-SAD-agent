# P5-S51 规格与决策：DWG 上传 → LibreDWG 转 DXF → S50 审查链

日期：2026-09-29　状态：已交付　前置：P5-S50

## 问题

`.dwg` 是设计院最常见的交付格式，此前网页端直接拒收，只能提示用户"另存为 DXF"。
ezdxf 只能读 DXF。DWG 是闭源格式，必须先转换成 DXF。

## 决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 引擎用 **LibreDWG 0.14** 的 `dwg2dxf`（用户拍板）。镜像内**从 GNU 官方源码构建**：固定版本 + sha256 校验 + 多阶段构建，运行时镜像只拷贝 `dwg2dxf` 和 `libredwg.so`（约 18 MB） | Debian bookworm 和 trixie 都没有 libredwg 包（已实测）。ODA File Converter 闭源、需要注册，且依赖 Qt/X11 |
| D2 | 转换**只在入库流水线里由程序调用**，**不暴露给模型**；`Capability.EXECUTE_SHELL` 仍然对任何主体一律拒绝 | 模型无法触发子进程，也无法控制任何 argv。这是"入库侧受控子进程"，与 P3 D3 中"不可能做成模型工具"的判断一致 |
| D3 | 子进程约束：<br>- 固定 argv，`shell=False`，不走 PATH 查找；<br>- 输入输出都在只属于本次转换的临时目录里，固定文件名 `in.dwg` / `out.dxf`；<br>- 超时 60 s；<br>- `RLIMIT_AS` 1 GiB、`RLIMIT_CPU` 60 s、`RLIMIT_FSIZE` 200 MiB；<br>- 环境变量只保留 `PATH`、`LANG`、`LD_LIBRARY_PATH`；<br>- stdout/stderr 只保留末尾 2 KB 用于诊断，不回显给浏览器 | DWG 解析器面对的是不可信二进制输入，历史上出现过大量 CVE。必须把最坏情况限制在"这次上传失败"：不挂死 worker、不写满磁盘、不读到别的文件 |
| D4 | 转换出的 DXF 直接送进 S50 的 `review_uploaded_dxf`，**审查、摘要、分块、召回全部复用**；上传记录 `suffix=.dwg`，`extract_engine=libredwg-0.14+dxf-review` | 一条链，一套纪律 |
| D5 | 报告头注明"由 DWG 经 LibreDWG 转换"，并附上转换器的警告条数 | LibreDWG 的 DWG 读取属于"有损但可用"：部分对象（代理实体、部分动态块）会被跳过。必须如实告知 |
| D6 | 转换器不可用（本机或镜像没装）→ `UPLOAD_EXTRACTION_FAILED`，提示"服务器未安装 DWG 转换器，请另存为 DXF"；转换失败、超时 → 同一错误码，带原因 | 能力缺失要响亮报错，不静默降级 |
| D7 | 能力说明（`file_context`）与前端白名单随 `dwg_converter_available()` 推导 | S49 纪律：能力由运行时推导，不写死文案 |
| D8 | 许可：LibreDWG 是 **GPLv3**，以**独立进程**调用（不链接进 Python 进程）。镜像里保留其 `COPYING`，并在 `THIRD_PARTY.md` 注明源码获取方式 | 通过进程边界隔离，不把 GPL 传染到本项目代码；分发镜像时满足提供源码的义务 |

## 不做

- DWG 输出（`dxf2dwg`）：属于 P6-S1，而且写 DWG 在 LibreDWG 里仍是实验性功能。
- 对 R2018 以上新格式、带代理对象的图纸不作兼容性承诺。以真实样本实测为准。

## 验收

- 用户提供的 4 张真实 DWG（R14 / R2004 / R2007，36 KB 到 500 KB）：转换耗时 ≤ 0.1 s，审查通过，摘要可读。
- 镜像内 `dwg2dxf` 的输出与 macOS 版字节差异只出现在时间戳字段。
- 伪造 DWG、截断 DWG、超时或超内存 → 400，不入库；临时目录已清理。
- `EXECUTE_SHELL` 相关断言不变；新增静态断言：`subprocess` 调用只出现在登记过的模块里。

## 实施记录与实测（2026-09-29）

**交付**
- `documents/dwg_convert.py`：受控子进程，约束见 D3。
- `.dwg` 进入上传白名单；迁移 `0007_step51_dwg_uploads`，`MIGRATION_HEAD` 三处同步。
- Dockerfile 新增 `libredwg` 构建阶段，运行时只保留 `dwg2dxf` + `libredwg.so` + `COPYING`/`SOURCE`。
- `THIRD_PARTY.md`。
- 前端白名单与卡片文案同步更新。
- 能力说明随 `dwg_converter_available()` 推导。

**实测中暴露并修复的 3 个问题**
1. **LibreDWG 写出的 DXF 开头带 `999` 注释**。这是合法 DXF，但 S50 的魔数校验太严，把它拒了。现在允许任意条 999 注释出现在开头。
2. **LibreDWG 读取自己 `dxf2dwg` 写出的 DWG 时，会给 ENDBLK 写出 `handle 0`**，ezdxf 因此拒绝打开整张图（`Invalid handle 0`）。修复方式是只删掉这一对组码，删掉的次数计入转换警告并如实披露。4 张真实 DWG 都没出现这个问题；测试夹具（合成 DWG）会出现。
3. **转换出的 DXF 文字里含孤立代理项**，护栏在 `encode("utf-8")` 时会让整张图崩溃。现在在读取器的文字入口处替换成 U+FFFD。

**性能修复**
- `单-1.dwg`（R2004，500 KB）转出 13,864 条管段、784 条标注。`map_pipes` 逐一计算点到折线的距离，共 1,090 万次，耗时 **5.76 s**。
- 在 `_nearby_annotations` 前加了包围盒预筛（盒外的点距离必然超过半径），耗时降到 **0.37 s**。
- 对 18 张真实 DXF 样图加这张 DWG 转换图，逐一对比新旧实现的管段、缺输入、发现项、未检查项：**19/19 完全一致**。

**真实 DWG 样本**（用户本机的 7 份，不入库）

| 样本 | 版本 | 大小 | 本机总耗时 | 管段 | 结果 |
|---|---|---|---|---|---|
| 单-1 | AC1018 | 499 KB | 6.66 s（修复前）→ 容器内上传 2.59 s | 13,864 | 通过 |
| 单-2 | AC1018 | 495 KB | 5.90 s（修复前） | 13,943 | 通过 |
| 5-圆形泵房_t3 | AC1018 | 163 KB | 0.32 s；容器内 0.75 s | 1,941 | 通过 |
| 给排水设计图例 | AC1021 | 211 KB | 0.17 s；容器内 0.29 s | 1,236 | 通过（转换器报告 2 条 ERROR，不影响） |
| 矩型化粪池、阀门井、隔油池 | AC1014 | 24–34 KB | ≤0.01 s | 2–9 | 通过 |

- 镜像内 Linux 版 `dwg2dxf` 与 macOS 版的输出，字节差异只出现在时间戳字段。
- 截断的 DWG 返回 400，错误为 `DWG 转换失败（退出码 1）：ERROR: Size underflow 306 for R2004_Header`，不入库。
- 容器（只读根文件系统，uid 10001）端到端：上传泵房 DWG 返回 201，接着附图提问，真实 DeepSeek 返回 `succeeded`，3 条引用都通过了校验。回答从图面文字里列出了离心泵、潜污泵、桥式起重机等设备，管径 DN600–DN300，阀门型号 Z945T-10、HH44T-10，以及黄海高程标高；它**主动指出** DN 编号是孤立文字、没有匹配到管段，并如实转述了转换警告（33 条，其中有匿名块 `A$C…`）。
- `docker compose run --rm smoke` 30/30；`check_image.sh` PASS（非 root、无密钥材料、构建上下文无泄漏）。
- 镜像体积 615 MB；LibreDWG 构建阶段冷启动约 7 分钟，有缓存时跳过。

**残余**
- 转换器报告的"警告"数把 ERROR 和 Warning 行都计入，口径偏粗；33 条警告具体丢了哪些对象，没有逐条解析。
- R2018 以上版本和带代理对象的图纸没有真实样本，不作兼容性承诺。
- CI 每次冷构建都要多花 7 分钟（p5-compose 没有层缓存）。可以考虑推一个预构建的 LibreDWG 基础镜像，这是后续待办。
- 子进程的 `RLIMIT_AS` 在 macOS 上无法收紧，只在 Linux 镜像里生效；本机开发环境只靠超时和 CPU 上限兜底。
