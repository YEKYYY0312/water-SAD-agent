## 0. 最重要的结论（先说）

**规格 §5 与当前语料状态相冲突，冲突以规格为准。**

规格 §5 禁止缓存「实时或**版本未知**的结果」。而 `data/versions.json` 的 4 本规范
（GB50015-2019 / GB50013-2018 / GB50014-2021 / GB50318-2017）状态**全部为 `unknown`**
（AGENTS.md 已登记为 blocked 项，待人工核实）。

严格执行的直接后果：**当前真实语料下，任何回答都不满足写入资格**，
disposition 原因为 `spec_version_unknown`。

我按规格字面执行（fail closed），并把这个事实做成**显式断言**
（`TestRealCorpusCurrentlyIneligible`，3 条测试，含直接读 `data/versions.json` 的双保险）。

- 缓存机制完整、可测（80 条测试全绿）；
- 但**今天的命中率是 0**，且这是设计意图，不是缺陷；
- **人工核实 `versions.json` 就是解锁缓存的开关** —— 核实后缓存自动生效，
  相关测试会失败并提示更新（那正是"解锁"信号）。

拒绝的替代方案：为提高命中率把版本校验放宽（例如"unknown 也算可缓存"）。
那会让过期规范的答案被长期复用 —— 在给排水设计场景里，这比缓存失效严重得多。

## 2. 候选方案与取舍

### D1 版本 unknown 时怎么办（本步最关键的决定）

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| unknown 也允许缓存，靠 TTL 兜底 | 过期规范答案被复用到 TTL 结束；违反规格 §5 明文与铁律② | 拒绝 |
| 加"宽松模式"开关，默认关 | 开关本身就是绕过路径；且没人会记得它是关的 | 拒绝 |
| **严格 fail closed，并把现状做成显式测试** | 机制完整可测；解锁条件明确且可执行；不牺牲正确性 | **采纳** |

### D2 缓存键用「本次引用的规范版本」还是「注册表全量快照」

这是实现中发现的**真实陷阱**：`lookup` 发生在检索**之前**，那时还不知道会引用哪些条款。

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 用本次引用的 spec 版本摘要 | 查时摘要为空、写时非空 → **查写键永不相同，缓存永远命中不了** | 拒绝 |
| 不把版本状态入键 | 违反规格 §5「规范版本状态」必须入键 | 拒绝 |
| **用注册表全量状态快照** | 查写两侧一致；版本状态变化同样导致失效 | **采纳** |

代价：任一规范状态变化会失效**全部**缓存，而非仅相关条目。
在当前 4 本规范、单机使用的规模下这个代价可忽略；且偏向"过度失效"而非"错误复用"。

### D3 `CacheDisposition` 的 `status` 与 `eligible_for_store`

Step 11 已把两者拆开（当时的理由是"MISS 且不可存"必须可表达）。
**Step 13 验证了这个设计是对的**：`INELIGIBLE` + `eligible_for_store=False`
携带稳定 reason（10 种），使"为什么没缓存"在 trace 里一目了然。
若当初合并为单一状态，`spec_version_unknown` 与 `citation_not_verified`
就会被压成同一个"没缓存"。

### D4 `no_cache` 与 `no_store` 的语义分离

| 选项 | 语义 | 用途 |
| --- | --- | --- |
| `no_cache` | **不读**但仍可写 | 强制刷新（怀疑答案过期） |
| `no_store` | **不写**（读不受影响） | 敏感请求不留痕 |

`no_cache` 的 lookup 返回 `BYPASS` 而**不计 miss** —— "没查"和"未命中"是不同的事实，
混淆会污染命中率指标。

### D5 规范化的边界（防语义缓存滑坡）

采纳**保守规范化**：NFKC（处理全角/半角，中文输入法常见）+ 空白折叠（排版差异）。

**刻意不做**：大小写折叠、同义词、词干化。理由：`GB50015` 与 `gb50015` 折叠看似无害，
但这条路的下一步就是"设计秒流量"与"秒流量"合并 —— 那已经是语义缓存。
`test_paraphrase_does_not_hit` + `test_cache_module_has_no_embedding_dependency`
（断言 cache.py 不含 `embed`/`similarity`/`cosine`/`vector`）把这条线钉住。

### D6 语料版本用内容摘要而非时间戳

`manifest.json` 有 `created_at`，但重建语料而内容未变时它也会变 → 无谓清空缓存。
**采纳**对内容字段（`included_specs`/`records_included`/`source_files` basename/
`included_by_label`）取摘要；时间戳只在内容字段都读不到时兜底。
manifest 缺失/不可解析 → `CORPUS_VERSION_UNKNOWN` → 不读不写（fail closed）。

### D7 prompt cache 观测：VERIFIED 还是 DOCUMENTED_UNVERIFIED

规格 §5：「若 provider 支持方式未以官方文档和实际 usage 证实，只能保留 cache-friendly 提示布局」。

字段路径（`prompt_tokens_details.cached_tokens` / `prompt_cache_hit_tokens`）依官方文档编写，
但**无 Key 环境下未用真实响应证实**。因此 `observe_prompt_cache` 恒返回
`DOCUMENTED_UNVERIFIED`，**永不返回 `VERIFIED`**，并有测试断言这一点。
有 Key 抽查确认后才可改。

`cached_tokens=None`（字段缺失）与 `=0`（有字段但未命中）是**不同的事实**，
trace 中前者不写该键，后者写 0。

## 4. 缓存键的 10 个失效因子

规范化 query、主体+授权域、模型、温度、prompt 模板版本、工具策略版本、
语料+索引版本、规范版本状态摘要、检索参数摘要、条目格式版本。

每一个都有独立的 miss 测试（`TestInvalidationFactors`，10 条参数化）。
`CacheKeyFactors` 是 `extra="forbid"` + `frozen` —— 新增失效维度必须改契约，
不能靠额外字段偷偷混入。

## 5. 明确拒绝的做法

- ❌ **不做语义缓存**（规格 §1.2）：规范问答引用要求严格，语义相似 ≠ 同一设计条件。
  需独立 gold + 误命中率证据 + 人工批准，另开 P2.6。
- ❌ **不为提高命中率放宽版本校验**（见 §0）。
- ❌ **不按 `skill-cost-patterns` 的命中率区间（"10-25%"/"40-60% for FAQ bots"）
  写入文档或作为目标**：那是示例数据，本项目命中率结构性为 0。
- ❌ **不做工具按意图裁剪**：工具定义是当前最大静态开销（~3412 tokens），
  `prompt-context-optimizer` 建议按意图裁剪。但那会改变模型可见的工具集，
  **需先有工具选择准确率的独立评测**（否则可能让模型选不到该用的工具）。
  当前 4 个工具全量暴露，已有测试钉住上限（< 4500 tokens）防止无声膨胀。
- ❌ **不做历史摘要/截断**：规格 §5「P2.5 不可静默丢失历史」。
  当前 checkpointer 保留完整 state。已加测试断言 `assembler.py` 不含裁剪逻辑
  （`messages[-`/`history[:`/`summarize_history`/`drop_oldest`），
  将来若加入必须先有独立评测。
- ❌ **不启用 provider prompt cache 的主动配置**（如 Anthropic 的 `cache_control`）：
  DeepSeek 的支持方式未经真实响应证实，只保留 cache-friendly 布局
  （`assembler.py` 已是稳定段在前）。
- ❌ **不做持久化缓存**：内存实现无落盘，因此不存在"运行时缓存目录需删除路径"问题。
  未来若加持久化 adapter，必须实现 `purge()` 的磁盘清理。

## 6. 上下文预算审查（prompt-context-optimizer 协议）

**实测数字**（`_estimate_tokens`，中文约 1 token/字符）：

| 组件 | 实测 tokens | 预算 | 占比说明 |
| --- | --- | --- | --- |
| 系统提示（4 段装配） | **1424** | 2120（段预算之和） | 67% 预算利用率，健康 |
| 工具定义（4 个 schema） | **3412** | 无硬上限（测试钉 < 4500） | **当前最大静态开销** |
| 检索片段 | 随 top_k 变化 | `legacy` 截断 400 字符/条 | 已有截断 |
| 会话历史 | 完整保留 | 无摘要 | 规格禁止静默丢失 |
| 生成保留 | 未显式设置 | — | 见下方残余项 |

**Top 3 浪费源**（按 Prompt 的 §2 协议）：

1. **工具定义静态开销 3412 tokens**，且**每次请求全量发送**。4 个工具中
   `material_stats` 的 schema 最大（嵌套 `PipeSegmentArgs`）。
   修法是按意图裁剪 —— 但需先有工具选择准确率评测（见 §5 拒绝项）。
2. **`version_snapshot` 段当前信息量为 0**：4 本规范全是"状态未知（待人工核实）"，
   占 ~120 tokens 却不提供任何有效约束。人工核实后这段才有价值。
3. **生成保留未显式设置**：`max_output_tokens` 在 `ProviderCall` 契约里存在，
   但当前调用方未传。不是浪费，是缺乏上限保护 → 登记为残余项。

**排序分析（lost-in-the-middle）**：系统提示已是"稳定段在前、易变段在后"
（缓存友好），user query 在最后（注意力最高处）。检索片段按相关度排序（rerank 后）。
**无需改动**。

## 7. 风险与残余问题

**本步引入的风险**：
1. **全量版本摘要导致过度失效**（D2 的代价）：任一规范状态变化会失效全部缓存。
   当前规模下可忽略，且偏向安全侧。
2. **进程内缓存不跨进程**：与 Step 12 的限流/预算同样局限。
   本实现无持久化，因此不存在跨进程读到脏数据的风险（只是命中率更低）。
3. **`_estimate_tokens` 是字符数粗估**：上下文预算断言用它，与真实 tokenizer 有偏差。
   仅用于"防膨胀"的相对比较，不作账单依据。

**Step 13 未收口（诚实记录）**：
1. **缓存未接进 RAG 图**：`AnswerCacheService` 已就绪并有完整测试，但
   `graphs/rag.py` / `cli.py::run_once` 尚未调用它。
   **理由**：当前语料下写入资格恒为 false，接线不会产生任何命中，
   却会给 RAG 主路径引入一条无收益的分支。接线留到版本状态核实后一并做，
   届时可用真实命中验证 —— 而不是现在接一条走不通的路。
   `provider_call_count == 0` 的断言已在 `TestHitAndProviderCallCount` 用服务层验证。
2. **judge 自建缓存未并入**：`data/eval/judge_cache/` 仍是独立实现。
   经核查其缓存键**已包含 context**（`_judge_cache_key`，含 query/answer/context/criteria/model）
   —— AGENTS.md 遗留清单里「LLMJudge 缓存键不含 context」这条**已过时**，本步已更正。
   但它仍缺 prompt/policy/corpus 版本维度，并入统一 `AnswerCache` 属独立改动。
3. **`max_output_tokens` 未在调用方设置**（见 §6 第 3 项）。
4. **prompt cache 字段未经真实响应验证**（D7）。
5. **缓存指标未聚合导出**：`CacheStats` 已就绪，聚合到报告属 Step 15。
