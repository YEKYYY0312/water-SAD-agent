**当前无任何主体可获得** —— `Principal` 构造期就拒绝授予（`DANGEROUS_CAPABILITIES`），
所以"P2.5 默认拒绝危险能力"是可测试的断言，不是一句承诺。

**注册点**（两处，Step 14 已覆盖）：
- `cli.py:396`（agentic 会话 registry）
- `harness/runner.py:631`（real-agentic 评测 registry）

两处都是裸 `ToolRegistry()`，**无需逐处接线**：`ToolRegistry._resolve_pipeline()`
在未注入时回落到进程级默认 `default_guardrail_pipeline()`。这是刻意的设计 ——
可选参数若在缺省时**跳过**治理，就等于给每个新调用点留一个绕过后门
（`skill-guardrail-patterns` 的 “Guardrails as a library import, not a middleware” 反模式）。
`tests/test_tool_policy.py::TestNoBypass` 断言裸构造的 registry 同样受护栏约束。

**护栏在 schema 校验之前**：`invoke()` 先 `validate_tool_call`，再
`args_model.model_validate` —— 顺序本身是安全属性（有测试）。但**缺参仍返回
`INVALID_ARGUMENTS` 而非 `GUARDRAIL_BLOCKED`**：护栏只看注入/能力/大小/allowlist，
不替代业务校验，否则「缺参澄清」这条正常路径会被伪装成安全阻断。

**材料导出**（`materials/export.py` 写 `.xlsx`/CSV）当前由 CLI 显式触发，
不是模型可调用的工具，因此不在工具清单里，**也因此未接护栏路径校验**
（路径由用户直接指定，不是模型决定的路径 —— 风险性质不同，但已登记为
威胁模型 §5 第 19 项的已知缺口）。若将来把导出暴露为工具，
必须登记 `EXPORT_TO_ALLOWED_DIR` 并给 `DEFAULT_TOOL_POLICY.allowed_export_dirs`

## 3. 静态扫描如何保证清单不被绕过

`inventory.py` 的 `scan_remote_egress_modules()` 按代码特征扫包内所有 `.py`：

```python
_EGRESS_PATTERNS = (urlopen, ChatOpenAI, OpenAIEmbeddings, httpx.*, requests.*,
                    http.client.HTTPS?Connection（P7-S8）)
```

- `ungoverned_egress_modules()` = 扫描结果 − 清单登记 → **必须为空**。
- `undeclared_tool_names()` = 代码里的 `ToolSpec(name=...)` − 清单登记 → **必须为空**。
- 两项都有反例保护测试（`test_scan_actually_finds_known_egress`），
  确认扫描器不是空断言。

**扫描的局限（诚实记录）**：
1. 只匹配上述 6 类特征（`http.client` 连接类由 P7-S8 加入）。若将来引入别的 SDK 入口（如 `anthropic.Anthropic()`、
   `aiohttp`），**必须同时把新特征加进 `_EGRESS_PATTERNS`**，否则扫描形同虚设。
2. 只做文本匹配，不做导入图分析 —— 无法发现"通过动态字符串构造 URL 再间接调用"的路径。
3. `inventory.py` 自身在豁免名单里（它的源码含这些模式字符串）。
4. 扫描范围是 `src/water_agent/`，**不含 `scripts/`**。`scripts/build_index.py` 等
   离线脚本的远程调用需 Step 12 单独确认。
