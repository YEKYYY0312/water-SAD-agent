## 2. architecture-reviewer scorecard（0–3）

评分只依据**代码中真实存在的东西**，不给"计划中"加分。

| 组件 | 分 | 状态 | 依据 |
| --- | --- | --- | --- |
| API Gateway（auth/限流/CORS） | 0 | 不适用于当前形态 | 无 HTTP 服务；P4/P5 职责。契约已预留 `Principal` |
| Input Guardrails | 1 | 仅局部 | 无注入/PII 检测；仅 `ToolSpec.description` 有注入标记校验 |
| Prompt Management | 2 | 较完整 | 分段装配 + 段级预算 + `RuntimeContextProjection`；无 A/B 与版本回滚 |
| Context Assembly | 3 | 生产可用 | RAG + function calling + checkpointer 记忆 + rerank |
| Answer Cache | 0 | 无 | 仅 judge 有自建缓存，且键不含 context（已知缺陷） |
| LLM Caller（重试/超时/流式） | 1 | 不完整 | 6 个出口散落；2 处无超时、3 处无重试；无熔断 |
| Output Guardrails | 2 | 领域侧强、通用侧无 | `validate_citations` + docgen 数值/结构自检（**强于通用建议**）；无 PII/secret 输出检查 |
| Cost Tracker | 1 | 仅估算 | `generation/cost.py` 估算 + trace `llm_call` 事件；无账本、无预算、无 `usage_known` 语义 |
| Eval Logger | 3 | 生产可用 | 双轨 harness、baseline 对比、`compare_baseline.py`、CI 门禁 |
| Observability | 2 | 较完整但有泄漏面 | JSON trace + OTel 接口；`_serialize` 会写条文全文（T9） |

**总分 15/30。** 结论与规格一致：**评测与领域校验链已经很强（这是本项目的相对优势），
运行时治理（限流/预算/缓存/护栏）基本为零**。

按 Prompt 的风险分级映射到本项目的真实可达性（**不照抄"P0 = 无限流即 ship blocker"**，
因为当前没有公网入口）：

- **P0（当前）**：无 —— 无公网暴露，Key 未硬编码，计算与引用有确定性校验。
- **P1**：间接注入无防线（T1）；6 出口无统一可靠性边界（T5）。
- **P2**：无用量账本与预算（T5）；trace 可能含原文（T9）。
- **P3**：无缓存（成本）；无并发/水平扩展考虑（当前单机无需）。
- **一旦 P4/P5 上线**：无限流、无认证、无 CORS 立刻升为 P0 —— 故契约必须现在预留。

## 3. safety-auditor 威胁清单

完整清单见 `docs/design/p2.5-threat-model.md`（T1–T11，含攻击向量、已有控制、残余风险、
P4/P5 后评级变化）。此处只记本 Step 得出的**两个判断**：

1. **头号风险是间接注入（T1），不是直接注入（T2）**。单机用户没有动机攻击自己；
   真实入口是条文语料、用户管段表、以及 P3 的 DWG 文本。因此 Step 11 的契约投资
   优先放在**来源标签的不可提升性**上，而不是"越狱检测"。
2. **本项目已有的 `validate_citations` 是当前最有效的注入防线** —— 它把"模型被诱导
   编造引用"变成结构化失败。Step 14 的护栏必须**与它组合**，而不是替代它
   （规格 §6 明确要求）。

## 4. 候选方案与取舍

### D1 契约放在哪里

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 扩展 `domain/models.py` | 治理与领域模型耦合；`domain` 已被图/工具/检索广泛导入，易生成循环依赖 | 拒绝 |
| 新建顶层 `governance/` 包 | 与 `runtime/` 语义重合，规格原文写的是 `runtime/governance/` | 拒绝 |
| **新建 `runtime/governance/`** | 与 `graphs/`/`tools/`/`retrieval/` 并列的跨切面层；只反向依赖 `domain`（复用 `content_hash_of`/`utc_now` 的哈希口径） | **采纳** |

补充约束：本层**不得** import langchain/langgraph，并用测试锁死
（`TestGovernanceLayerHasNoFrameworkDependency`）。理由：治理契约要能在纯离线单测中构造，
且 Step 12 的 gateway 必须可被 fake transport 注入。

### D2 来源标签如何做到"不可由模型/用户声称"

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 字符串字段 + 文档约定 | 正是规格 §3 禁止的"可自由声称的字符串" | 拒绝 |
| 枚举 + 运行时检查散落在调用点 | 每个新调用点都可能忘记检查 | 拒绝 |
| **枚举 + 代码定义的信任偏序 + `relabel` 单调性检查** | 提升信任度的重标记**在契约层抛异常**，与调用点纪律无关 | **采纳** |

关键设计：`INSTRUCTION_BEARING_SOURCES` 只含 `SYSTEM_POLICY`。
这让"检索条文里的指令只能当数据"成为一个可断言的属性
（`test_retrieved_clause_is_data_not_instruction`），而不是提示词里的一句话 ——
`skill-injection-defense` 的硬拒绝项之一正是「"Trust me, the system prompt handles it."」。

### D3 危险能力：不实现，还是登记后拒绝

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 不定义 write_file/shell 等能力 | "默认拒绝"变成"尚未实现"，**无法写反例测试**，P4 加工具时也无处挂钩 | 拒绝 |
| **登记进 `Capability` + `DANGEROUS_CAPABILITIES`，构造期拒绝授予** | `Principal.local(capabilities={WRITE_FILE})` 直接 `ValidationError`；4 个危险能力各有反例测试 | **采纳** |

### D4 `usage_known` 是布尔还是用 `None` 表达

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| token 字段为 `None` 即表示未知 | 无法区分"provider 没返回"与"字段忘了填"；也挡不住"填了估算值" | 拒绝 |
| **显式 `usage_known: bool` + 校验器禁止填充** | `usage_known=False` 时填任何金额直接 `ValidationError`（"估算不得当账单"） | **采纳** |

### D5 `CacheDisposition` 用单一状态还是拆两个字段

采纳**拆分**：`status`（hit/miss/bypass/ineligible）与 `eligible_for_store` 独立。
理由：必须能表达「MISS 且不可存」—— 例如引用校验未通过的答案。
若合并为单一状态，"未验证引用不得进缓存"就无法在 Step 13 被测试排除。

### D6 接入覆盖测试怎么做（规格要求 vs 当前可实现）

规格 §3 要求「测试能发现未通过 `ProviderGateway` 的远程调用；新增工具未经
`GuardrailPipeline` 时失败」。但 Gateway 属 Step 12、Pipeline 属 Step 14，**此刻不存在**。

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 跳过该测试到 Step 12/14 | 违反规格；且届时"哪些出口存在"已无真源，容易漏 | 拒绝 |
| 先写 skipped 占位测试 | 规格禁止用 SKIP 掩盖未实现 | 拒绝 |
| **清单作唯一真源 + 静态扫描断言"代码出口 == 清单"** | 现在就能失败：新增未登记出口/工具立即红灯。Step 12/14 只需把 `governed`/`guardrail_validated` 翻 `true` | **采纳** |

诚实记录扫描的 4 项局限（见 provider inventory §3）：只匹配 5 类特征、
不做导入图分析、`inventory.py` 自身豁免、不含 `scripts/`。
**新增 SDK 入口必须同时扩展 `_EGRESS_PATTERNS`**，否则扫描形同虚设 —— 这是本方案
最需要靠纪律维持的一环，已写进 provider inventory 的纪律段。

## 5. 明确拒绝的做法

- ❌ 不按 `prompt-cost-optimizer` / `skill-cost-patterns` 的示例价格与 DAU 阈值给成本投影。
  真实账单与用量是 `unknown`；`PRICE_UNKNOWN` 占位保留到人工确认。
- ❌ 不采纳 `skill-guardrail-patterns` 的「Layer 3 ML 分类器 / LlamaGuard / Presidio」作为
  P2.5 默认层。规格 §1.2：外部分类器只能是可选 adapter，确定性边界必须在本项目内；
  且本项目是本地 CLI，引入 GPU 依赖不成比例。
- ❌ 不做语义缓存（规格 §1.2）：规范问答引用要求严格，语义相似 ≠ 同一设计条件。
- ❌ 不在 Step 11 改任何业务回答内容、不接入真实分类模型、不动 6 个远程出口的调用代码。
- ❌ 不把 `ToolSpec.max_retries` / `timeout_seconds` 在本步删除。它们确实是死字段，
  但属 Step 12 的「接入或删除」范围，本步只登记（威胁模型 §5 第 7 项）。
- ❌ 不声称项目具备生产级缓存/限流/预算/内容过滤/认证授权。
  `governance_coverage()` 返回 `provider_governed: 0`、`tools_guardrail_validated: 0`，
  并有测试锁死这两个数（`test_no_site_claims_governed_before_step12`）。

## 6. 风险与假设

**假设**（若有误需修正本记录）：
1. 部署形态在 P4 前保持本地 CLI，无公网入口。
2. 条文语料 `data/curated/` 由本人策管，非任意第三方投稿 —— 这是 T1 当前评 High 而非
   Critical 的依据。
3. 条文本身是公开规范，不属机密；trace 中条文全文的风险主要在 query 与项目文档，不在条文。

**本步引入的风险**：
1. **文档与代码漂移** —— 三份 md 需人工同步；缓解：机器可读真源在 `inventory.py`，
   md 明确声明"不一致时以代码为准"。
2. **扫描特征不全** —— 见 D6；缓解：反例保护测试 + provider inventory 的纪律段。
3. **契约未被消费即失效风险** —— Step 11 只定契约，若 Step 12/14 另起一套则本步白做；
   缓解：`inventory.py` 的 `target_gateway_method` 字段已把 Step 12 的接口名钉住。
