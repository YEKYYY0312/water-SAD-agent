# 端到端走查（Worked Example）

> 把设计文档里的抽象图，落到 3 个代表性真实问题上的**具体过程**，帮你审设计时
> 一眼看清每一环。走查展示的是**设计行为**（是怎么设计的），不涉及实现代码。

---

## 场景 A —— 规范问答（RAG 环）

**用户问题**：`给水立管的最小公称直径是多少？`

**走查**：
1. **Router** 判定意图 = `rag`。
2. **RAG 子图**：
   - `retrieve`：把问题做 query 改写 → TriviumDB `search_hybrid`（向量 + BM25 多路召回）→ 返回命中条款，如 `GB50015-2019 5.4.2`、`4.4.5`。
   - `generate`：基于命中的条款正文生成回答，输出**引用列表** `["GB50015-2019 5.4.2"]`。
   - `self_check`：核对引用是否真实存在于语料、条号是否现行。若引用缺失/条号错误 → 带反馈回到 `retrieve`（最多 N 次）。
3. **Reflection**：再检查引用精度、是否回答了「公称直径」这个具体口径。
4. **输出**：回答 + 条款引用卡片。

**Harness 如何判分**：规范问答用例 → `rag` 类型，判分 = **引用可追溯（是否命中真实存在的条款）+ LLM-judge（回答是否准确）**。

---

## 场景 B —— 水力计算（计算环 + 回环）

**用户问题**：`DN150 管，流量 20 L/s，求流速并判断是否满足给水要求。`

**走查**：
1. **Router** 判定意图 = `calc`。
2. **计算子图**：
   - `parse`：从问题提取参数 `{diameter_mm:150, flow_lps:20}` 与目标 `velocity`。
   - `compute`：调用水力计算工具（或 MCP `calculate_velocity`）→ `v = 4Q/(πd²) ≈ 1.13 m/s`，`unit=m/s`、`formula=…`。
   - `validate`（程序化校验）：1.13 落在合理流速区间（如 0.6~1.5）→ `ok`。
   - （若超界，如 `60 L/s` → v≈3.4 m/s 超上限 → 触发回环 `_revise` 提升管径 → 重算 → 直到达标或达上限）。
3. **Reflection**：校验依据（如给水最大流速 2 m/s，摘自规范引用）。
4. **输出**：`流速 1.13 m/s + 单位 + 公式口径 + 规范引用`。

**Harness 如何判分**：计算用例 → `calc` 类型，判分 = **程序化数值比对**（相对误差 ≤1%），不依赖 LLM 判分。

---

## 场景 C —— 文档生成（Human-in-the-loop）

**用户问题**：`根据上面的计算，生成这段给水系统的设计说明。`

**走查**：
1. **Router** 判定意图 = `docgen`。
2. **文档子图**：
   - `gather_inputs`：收集前面的计算结果 + 规范引用 + 项目参数。
   - `draft`：模板化生成设计说明草稿。
   - `self_check`：检查是否引用了正确的规范、数值是否与计算一致、口径统一。
   - **`approval`（interrupt）**：**暂停等待人工确认** —— 用户确认后才产出正式文档；不确认可返回修改。
3. **输出**：正式设计说明 + 所需确认记录。

**Harness 如何判分**：文档用例 → 判分 = **计算书合规性**（结构/数值一致性 + 引用正确）+ 人工确认节点的存在性与可恢复性。

---

## 三种能力在 Harness 中的定位

| 能力 | Loop 类型 | 判分策略 | 硬门槛 |
|---|---|---|---|
| 规范问答 | RAG 环 | 引用可追溯 + LLM-judge | 不编造条款 |
| 水力计算 | 计算环 | **程序化数值比对** | 误差 ≤1% |
| 文档生成 | 文档环 + Human-in-loop | 计算书合规性 + 一致性 | 数值一致、引用正确 |

> 走查揭示的设计要点：**自定义语言的自然语言→参数提取**（场景 B 的 `parse`）是后续
> 需要 LLM 或规则介入的关键；计算类一旦`validate` 由程序化兜底，就不会因 LLM 口算出错。
