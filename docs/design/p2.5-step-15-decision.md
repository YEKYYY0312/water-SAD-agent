### 2. 基于 Trace 的失败模式检测器（8 个，`src/water_agent/runtime/governance/detectors.py`，620 行）

**检测器清单**（版本 `p2.5-step15-2026-09-06`）：

| 检测器 | 严重度 | 触发条件 | Runbook 要点 |
|--------|--------|----------|--------------|
| `guardrail_bypass` | PAGE | 工具执行事件无配对护栏事件（按 `invocation_id`） | 检查工具调用站点是否传递 `trace`，回溯绕过路径 |
| `tool_misuse` | TICKET | ≥2 次 `INVALID_ARGUMENTS` 错误 | 检查工具 schema、提示语澄清 |
| `cascading_errors` | TICKET | 连续 ≥3 个错误事件 | 检查熔断是否生效、重试上限 |
| `context_loss` | TICKET | 有检索但成功结束却零引用 | 检查引用校验器是否接入、回流逻辑 |
| `hallucinated_action` | PAGE | 引用的 source_id 不在检索结果内 | 检查引用校验器、模型幻觉 |
| `success_hallucination` | PAGE | 护栏 BLOCK 但 status=succeeded | 检查 finalize 节点是否尊重护栏决定 |
| `unverified_citation_after_cache` | PAGE | 缓存命中后产出未验证引用 | 检查缓存写入资格、引用校验顺序 |
| `budget_bypass` | TICKET | 有计费 LLM 调用但无 usage 事件 | 检查 gateway 是否接入（已知限制：同 trace 内多次调用会误报） |

**三条纪律**（规格 §7 + `skill-failure-detector` hard rejects）：
1. **必须版本化**：`DETECTOR_VERSION="p2.5-step15-2026-09-06"`，退化会静默摧毁信号
2. **不得调用 LLM**：每条 trace 调模型判定会让账单翻倍、可用性绑到 provider、判定不可复现；有 AST 静态断言禁止导入 `openai/anthropic/langchain*/requests/httpx/urllib/socket`
3. **不得只在崩溃时打标**：绝大多数 Agent 故障产出看起来正常的输出；必须在 `status=succeeded` 的 trace 上也能检出（有测试断言护栏阻断+成功状态 → `success_hallucination` 必须命中）

**证据脱敏**：
- `signals_to_payload()` 返回的 JSON 可含规则 ID（排障需要），但**不得含攻击载荷原文**（"忽略以上"/"PWNED"/手机号/sk- 等）
- 有测试断言 `success_hallucination` 的证据 blob 不含已知攻击 token

**配对机制**（`guardrail_bypass` 检测器核心）：
- 工具执行事件（`record_tool_event`）与护栏事件（`record_guardrail_event`）都带 `invocation_id`
- 配对靠 ID 而非事件相邻（并发/重试会让相邻性给出错误结论）
- 只有 `stage="tool"` 的护栏事件才能配对工具执行（`stage="input"` 不能顶替）
- 已接入 `ToolRegistry.invoke` 的所有返回路径（success/validation-error/block/execution-error/timeout）

## 关键设计决策

### 决策 1：检测器不调 LLM，用确定性规则

**背景**：规格 §7 与 `skill-failure-detector` 都要求"不得每条 trace 调模型做判定"。

**理由**：
- 每条 trace 调模型会让观测成本与可用性绑到 provider：账单翻倍、provider 挂了就看不见故障
- LLM 判定不可复现（非确定性输出 → 无法回溯）
- 当前 8 个检测器都是结构化断言（事件存在性、计数、字段值匹配），无需语义理解

**实现**：AST 静态断言 `detectors.py` 不导入任何 provider SDK 或网络库。

### 决策 2：未知值记 `None` 不记 `0.0`

**背景**：指标如 `cache_hit_rate` 在无缓存事件时是"不可计算"还是"0"？

**理由**：
- `0.0` 会让人以为"缓存在跑但一次没命中"，而事实是"根本没接缓存"
- 与现有项目纪律一致（`UsageRecord.usage_known=False` 时禁止填 token/成本）
- 有测试断言：无缓存事件 → `hit_rate=None`；有事件全 miss → `0.0`

**实现**：`GovernanceMetrics` 所有比率/成本字段类型为 `float | None`；aggregation 逻辑检查分母是否为 0 或事件缺失。

### 决策 3：不假装已发送 PagerDuty/Slack

**背景**：规格 §7 明确"不得谎称已投递外部告警"。

**理由**：
- 谎称"已告警"比不告警更危险：让人以为安全团队已收到，实际上没人知道
- 当前项目无 PagerDuty/Slack 配置，接入外部投递通道需单独决策
- 本地结构化事件已足够：可被聚合、可写盘、可被外部系统读取

**实现**：
- `Alert.delivery="local_event_only"` 恒定，无可配置项
- AST 静态断言 `observability.py` 不导入任何出站库、不含 `http://` 或 `https://` URL 字面量
- 模块 docstring 诚实声明"不假装已发送 PagerDuty / Slack"（AST 检查会跳过注释，不会因说明而误判）

### 决策 4：`by_detector` 计 trace 数不计信号数

**背景**：一条 trace 可能产生多个同类信号（如 2 次 `INVALID_ARGUMENTS` → 1 个 `tool_misuse` signal），聚合时计什么？

**理由**：
- 告警阈值语义是"多少比例的 trace 有问题"，不是"产生了多少信号"
- 混用信号数会让阈值失去意义（同一问题的多次重试会被计多次）
- `SignalDistribution.by_detector` 用 `dict[str, set[trace_id]]` 去重后再计数

**实现**：
- `tag_traces()` 返回 `(per_trace, dist)`，`dist.by_detector[name]` 是命中该检测器的 trace 数
- `dist.rate_for(name)` = `count / total_traces`
- 有测试断言：2 条 trace 各产生 2 个信号 → `by_detector[name]=2` 不是 4

### 决策 5：场景用注入时钟，不真实 sleep

**背景**：场景测试"限流恢复"和"熔断半开"需要时间推进，真实 sleep 会让测试慢且不稳定。

**理由**：
- 确定性：手动推进时钟 → 结果可复现
- 速度：32 条场景 <10ms 总耗时
- 可测性：可精确控制时间点，测边界条件

**实现**：
- `_FakeClock` 类：`now` 属性 + `advance(seconds)` 方法
- 注入到 `ProviderGateway(clock=fake_clock)` 和 `RateLimitStore(clock=fake_clock)`
- 场景内调用 `clock.advance(60)` 推进 1 分钟，无真实等待

### 决策 6：工具事件与护栏事件通过 `invocation_id` 配对

**背景**：`guardrail_bypass` 检测器需判断"工具执行了但无护栏裁定"，如何配对？

**理由**：
- 事件相邻不可靠：并发/重试会让护栏事件与工具事件不相邻
- 时间戳不可靠：同一 ms 内可能有多个事件
- `invocation_id` 是执行的唯一标识，天然适合配对

**实现**：
- `record_tool_event()` 和 `record_guardrail_event()` 都接受 `invocation_id` 参数
- `detect_guardrail_bypass()` 构造两个集合：executed tool invocations、guardrailed tool invocations（只计 `stage="tool"`）
- unpaired = executed - guardrailed，非空即报 PAGE

**测试覆盖**：
- 配对正确 → 不报
- ID 不同但相邻 → 报（证明不靠相邻）
- `stage="input"` 不能顶替 `stage="tool"` → 报

## 已知限制

### 1. 检测器尚未接进 CLI/runner 生产调用站点

**现状**：
- `record_tool_event()` 和 `record_guardrail_event()` 已接入 `ToolRegistry.invoke` 和 `GuardrailPipeline.validate_*`
- 但 CLI（`cli.py:396`）和 runner（`runner.py:631`）构造裸 `ToolRegistry()` 时未传递 `trace` 参数
- 默认 `trace=None` → 事件记录为 no-op，检测器无数据可分析

**影响**：检测器在评测套件内工作正常，但真实会话产生的 trace 缺工具/护栏事件，`guardrail_bypass` 等检测器无法生效。

**解锁路径**：
1. 在 CLI/runner 的 session/run 入口构造或读取 trace dict
2. 传递给 `ToolRegistry(trace=trace_doc)` 或在调用 `invoke()` 时传 `trace=` 参数
3. 运行后调用 `tag_trace(trace_doc)` 获取信号，写入观测系统

### 2. 告警路由未接外部投递通道

**现状**：`Alert.delivery="local_event_only"`，`write_alert_events()` 只写本地 JSONL。

**影响**：告警不会主动通知人，需外部系统轮询读取 `.jsonl` 或解析 CI 输出。

**解锁路径**（需单独决策）：
1. 配置 PagerDuty/Slack webhook
2. 扩展 `write_alert_events()` 或新增投递函数，根据 `severity` 路由
3. 更新 `Alert.delivery` 字段为实际投递结果（`pagerduty_sent`/`slack_sent`/`delivery_failed`）

### 3. `budget_bypass` 检测器已知误报

**现状**：同一 trace 内多次 LLM 调用时，检测器会对每次调用判断"有 `llm_call` 事件但无对应 usage 事件" → 实际 usage 事件可能在 trace 末尾统一记录，导致前面的调用被误判。

**影响**：`budget_bypass` 告警可能包含假阳性。

**解锁路径**：
1. 改为检查"trace 内 `llm_call` 事件总计费 token 数" vs "trace 内 `usage` 事件总 token 数"（全局对账而非逐次）
2. 或要求 `record_usage_event()` 在每次 `llm_call` 后立即调用，与 `llm_call` 1:1 配对
3. 当前在 `evidence` 中声明 `known_limitation`，告知读报告的人此检测器有系统性误报风险

### 4. `check_memory_write` 未接 checkpointer

**现状**：`GuardrailPipeline.check_memory_write()` 已实现（检测记忆投毒），但 `session.py` 的 `SqliteSaver` 写入路径未调用该检查。

**影响**：恶意会话可能通过 checkpoint 注入指令到后续轮次。

**解锁路径**：在 `SqliteSaver.put()` / `.put_writes()` 前调用 `pipeline.check_memory_write(content)` 并处理 BLOCK 决定。

### 5. `materials/export.py` 未接护栏路径校验

**现状**：材料导出写 `.xlsx` / CSV 文件到用户指定路径，未调用工具策略的 `validate_file_path()`。

**影响**：可能写到未授权目录（如 `/etc`、`~/.ssh`）。

**解锁路径**：在 `export_to_excel()` / `export_to_csv()` 开头调用 `ToolPolicy.validate_file_path(output_path, mode="write", allowlist=...)`。
