## 2. 候选方案与取舍

### D1 gateway 如何接进 6 个出口而不留绕过后门

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| `gateway` 设为必填参数 | 所有调用方与既有测试都要改；改动面大且易漏 | 拒绝 |
| `gateway=None` 时跳过治理 | **出现"不传 gateway 即绕过"的后门** —— 正是规格 §1.2 禁止的「只在某个分支调用的辅助函数」 | 拒绝 |
| **`gateway=None` 时取进程级默认 gateway** | 既保持既有构造签名兼容，又**不存在绕过路径**：要么经注入 gateway，要么经默认 gateway | **采纳** |

实现见 `runtime/governance/binding.py::default_gateway`。

### D2 三个 chat 出口如何收敛

`docgen/quality.py:288` 与 `harness/llm_judge.py:249` 各自内联构造 `ChatOpenAI`。

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 各自包一层 gateway | 三处重复超时/重试/usage 提取逻辑，口径必然漂移 | 拒绝 |
| 在治理层实现 `BaseChatModel` 子类 | 治理层就得 import langchain，违反纯度约束（有测试锁死） | 拒绝 |
| **`generation/governed_chat.py::GovernedChatModel` + 三处统一走 `build_chat_model`** | 框架适配留在业务侧（与 `tools/ds_adapters.py` 同思路），治理层保持纯契约；出站模块从 6 个收敛到 4 个 | **采纳** |

**收敛的可测证据**：`scan_remote_egress_modules()` 现在只返回 4 个模块，
`docgen/quality.py` 与 `harness/llm_judge.py` 已不在其中
（`test_consolidated_chat_sites_no_longer_open_own_connections`）。

### D3 重试叠乘问题（本步发现的真实缺陷）

`ChatOpenAI` 自带 `max_retries`（默认 2）。若只在外层加 gateway 重试，
实际请求数会变成**两者之积**（3 × 3 = 9 次），远超配置意图，且 429 退避会双层叠加。

**采纳**：`build_chat_model` 显式设 `max_retries=0`，重试**唯一**由 gateway 承担。
同时补上原先缺失的 `timeout`（取自 provider 画像）。

### D4 错误分类的默认方向

| 候选 | 取舍 | 结论 |
| --- | --- | --- |
| 未知错误默认重试 | 放大故障与成本；对永久错误（如参数错误）重试毫无意义 | 拒绝 |
| **未知错误默认永久（零重试）** | 与 fail closed 同向：不确定就不放大 | **采纳** |

分类优先级：HTTP 状态码 → 超时/连接异常类型 → 异常类名特征。
- 401/403 → `PROVIDER_AUTH_FAILED`，**零重试且不计入熔断**（换 Key 才能解决，
  熔断只会误伤后续正确配置）。403 正是 rerank 的已知阻塞码。
- 408/429/5xx → 瞬时，有界重试。
- 其余 4xx → 永久，零重试。

### D5 预算：预留-对账-回滚三段

单纯"事后记账"挡不住超预算：并发请求都会看到旧余额。

**采纳**三段语义：
1. **预留**（发送前）：按预估 token 占额度；
2. **对账**（返回后）：释放预留，记入**真实** usage（不是预估值）；
3. **回滚**（失败时）：释放预留，不记消耗 —— 否则失败调用永久占额度。

`test_settle_uses_actual_usage_not_estimate` 断言预留 300 而实际只记 130。

### D6 成本上限默认不启用

`ModelPrice.confirmed=False`（DeepSeek 公开单价未与真实账单核对）。
**用未确认价格做硬拒绝 = 用估算当账单**，违反规格 §4。

**采纳**：`BudgetConfig.daily_cost_cap_usd` 默认 `None`；只有可直接测量的
`daily_token_cap` 做硬限制。价格仍用于**估算记账**（`UsageRecord.cost_usd`），
但不作拒绝依据。`BudgetPolicy` 默认 `WARN`；`DEGRADE` 在配置期即被拒绝
（`test_degrade_policy_is_rejected_by_config`）。

### D7 限流额度怎么定（不虚构"生产调优值"）

DAU/账单 unknown，所以**不假装这是调优值**。定位是**失控保护**：
挡住 agentic 循环失控、重试风暴，而不干扰正常人工使用。

- chat 默认：桶 200K token、1K token/s、120 RPM —— 人工提问不可能超过。
- **embedding 单独放宽**（`INGEST_RATE_LIMIT`：5M token、50K token/s、6000 RPM）。
  **这是本步发现的真实问题**：`scripts/build_index.py` 要对整个语料库逐块嵌入，
  若沿用 120 RPM，**正常入库会被自己的限流打断**。

### D8 `ToolSpec` 死字段处理（规格 §4 明确要求）

核查结果：`max_retries` 与 `timeout_seconds` **从未被任何执行路径读取**。

| 字段 | 处置 | 理由 |
| --- | --- | --- |
| `max_retries` | **删除** | 工具重试语义与远程调用不同：`retrieve_clauses` 内部的远程 embedding 重试已由 gateway 承担；纯计算工具重试无意义（同输入必得同输出）。保留不生效的字段会让读者以为重试已配置 |
| `timeout_seconds` | **接入真实语义** | `ToolRegistry.invoke` 以**协作式 deadline** 校验：执行后检查耗时，超时返回结构化 `TOOL_TIMEOUT` |

**为什么协作式而非杀线程**：规格 §4 明确禁止用杀线程破坏不可逆操作。
当前 4 个工具都是只读/纯计算，丢弃超时结果是安全的。
`test_timeout_does_not_kill_thread` 断言 execute 完整执行（副作用可见），只是结果被丢弃。
未来若加入写入类工具，需另设 deadline 协议。

### D9 校验放在 gateway 内还是外

**放在外**的两处（重要区分）：
- **embedding 维度校验**：是"库与模型配置不匹配"，不是 provider 不可用 ——
  既不该被重试，也不该记成 `PROVIDER_UNAVAILABLE`。
- **`LLMGenerator` 结构化引用解析**：是**模型输出契约违约**（铁律②），
  同理不该被重试或误记为 provider 故障。

## 3. 本步发现并修正的既有缺陷

1. **重试叠乘**（D3）：`ChatOpenAI` 自带重试未关。
2. **入库会被自己限流打断**（D7）：批量 embedding 需独立额度。
3. **`test_embedding_provider.py` 会真打网络**：`provider._request_embedding = fail`
   的补丁点在我第一版重构中失效，测试耗时从 0.05s 涨到 **56s**（真实网络超时）。
   已恢复 `_request_embedding` 为单一注入缝。
4. **Step 11 inventory 记错两处超时**：embedding 与 rerank 记为 30s，
   代码实际都是 60s。已修正。
5. **Step 11 inventory 缺一个维度**：「逻辑调用点」与「实际开 socket 的模块」是两件事。
   Step 12 收敛后 `docgen/quality.py` 不再自开连接，静态扫描随即报错 ——
   已新增 `egress_module` 字段区分，扫描断言改为对 `egress_module` 集合。
6. **`_is_transient_embed_error` 成为死代码**：判定逻辑已由 gateway 的
   `_classify_error` 统一承担。按同一纪律（不留看似生效的死代码）删除。

## 4. 明确拒绝的做法

- ❌ 不按 `skill-cost-patterns` 的 "Pricing reference" 或 "Benchmark thresholds by scale"
  设定阈值：那是示例数据，本项目账单为 `unknown`。
- ❌ 不做 `prompt-cost-optimizer` 要求的成本投影与 before/after 节省表：输入全为 unknown。
- ❌ 不做模型路由（`skill-cost-patterns` 的 "Model routing rules"）：
  规格 §4 要求模型降级须先有独立配置、质量评测与审批；P2.5 默认不启用。
- ❌ 不用单进程 dict 声称支持多实例限流：`supports_multi_instance` 恒为 `False`
  并有测试断言。真正的多实例需另写 Redis/Postgres adapter（不在 P2.5 范围）。
- ❌ 不做语义缓存、不做回答缓存（Step 13 范围）。
- ❌ 不接 `GuardrailPipeline`（Step 14 范围）：`tools_guardrail_validated` 仍为 0，
  有测试锁死。

## 5. 风险与残余问题

**本步引入的风险**：
1. **行为变更**：provider 错误现在包装为 `GovernanceError`（原为裸 `URLError`/`RuntimeError`）。
   原始异常保留在 `__cause__`，但**调用方若按具体异常类型 catch 会失效**。
   已核查并更新受影响测试；`docgen` 的 blocked 语义、harness 的 `RealComponentsError`
   路径均验证通过（全量 759 tests 绿）。
2. **默认 gateway 是进程级单例**：限流桶与预算账本跨调用共享（这是意图），
   但**多进程运行时各自独立计数**。已在 `supports_multi_instance=False` 中诚实标注。
3. **粗略 token 估算**（`len(text)`）只用于预留额度，不作账单。若估算严重偏低，
   预留不足可能让实际用量超出 cap 一个请求的量级 —— 测试断言了上界
   （`snap.spent_tokens <= 900 + 200`）。

**Step 12 未收口（诚实记录）**：
1. **`CallCategory.EMBEDDING_INGEST` 未接线**：`scripts/build_index.py` 的批量嵌入
   走的是 `EMBEDDING_QUERY` 分类。分类区分预算池的能力已在契约里，但入库脚本
   尚未显式传入该分类。
2. **`scripts/` 目录不在静态扫描范围**：Step 11 已记录此局限，Step 12 未扩展。
3. **无告警投递**：预算 warn 只落 `UsageRecord`/`BudgetSnapshot`，
   未发 Slack/PagerDuty（规格 §7 明确要求"未配置不假装已发送"）→ Step 15。
4. **usage 提取未经真实 provider 验证**：`_usage_from_payload` 与
   `usage_from_langchain` 的字段路径（含 `prompt_tokens_details.cached_tokens`）
   依据 OpenAI 兼容约定编写，**无 Key 环境下未用真实响应验证**。
   有 Key 时需抽查，缺失字段会正确降级为 `USAGE_UNKNOWN`（不会静默估算）。
