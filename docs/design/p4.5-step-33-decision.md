# P4.5 Step 33 决策记录：有界主编排、审批恢复与发布门

**日期**：2026-09-11
**状态**：Implemented
**范围**：仅接入 P4.5 `multi_agent` 主图、SqliteSaver 审批恢复与窄导出门；不修改既有
`qa`、`docgen`、`drawing_review` 路径，不新增公式、RAG、绘图或审查实现。

## 决策

1. `MultiAgentOrchestrator` 使用现有 LangGraph `StateGraph`，固定主链为
   `hydraulic -> design -> drawing -> review -> deterministic router`。四个阶段分别复用
   Step 29--32 的现有适配器，主图不复制任何公式、检索、图纸或审查逻辑。
2. 路由唯一依据仍是 `ReviewIssue.owner`。回流前按既有 `route_review` 检查冻结上限
   `24 / 2 / 2 / 2 / 3`；达到任一上限即 `blocked + MULTI_RETRY_EXHAUSTED`，不会再调用
   责任 Agent。
3. 审批在副作用之前执行 `interrupt`。`SqliteSaver` 是构建图的必需依赖；恢复时重新计算
   当前最终产物集 hash，并与中断前的 `approval_context_hash` 对比，不一致即
   `MULTI_APPROVAL_STALE`。
4. `ApprovalRecord` 新增可选的 `final_package_hash` 与 `expires_at`，以兼容旧持久记录；
   新记录必须把 `calc/design/document/drawing/review` 的 canonical collection hash 同时绑定到
   `artifact_collection_hash` 与 `final_package_hash`。`FinalProjectPackage.release_manifest_hash`
   使用同一完整 hash 口径。
5. `release_gate` 在导出前重算六项：`approval_exists`、`approval_not_expired`、
   `package_hash_matches`、`no_stale_artifacts`、`review_passed`、
   `no_unresolved_blocking_findings`。任一失败不进入导出；导出适配器异常固定收口为
   `failed + MULTI_EXPORT_FAILED`，不得写成 `succeeded`。
6. `assemble_export_path` 不再允许无批准调用。真实路径继续只由装配期的 staging/final 目录与
   `file_id` 组合，模型不能传入路径。
7. CLI 仅在显式 `--flow multi-agent`（或已有等价环境开关）下组装该图；默认 `qa` 与旧
   `docgen` 流程保持不变。

## 验收

- 四 Agent 全链、Review owner 回流、循环耗尽、interrupt/resume、跨 SqliteSaver 重开恢复均有行为测试；
- 未批准、拒绝、过期批准、审批后产物漂移、导出适配器失败均无法发布；
- release gate 六项真实重算，不使用预置通过标记或完美指标。

## 残余限制

- P0 发布仍是已验证的 schematic DXF 草图，不代表施工图、DWG 或真实 CAD/BIM 实机发布；
- 人工批准不替代注册工程师责任；
- `expires_at` 为本地审批记录时限，不构成企业身份认证或电子签章。

## 2026-10-01 补充：管段 ↔ 工况显式绑定；审批拒绝/漂移在 approval 收口；resume 不再毒化会话

review 2026-09-30 离线复现了两个缺陷（另含协调方追加的 resume 毒化与 CLI 挂起两项）：

- **多工况被压成单一 DN**：Design Agent 取全项目第一个 DN 套给所有管段，每段管引用全部工况。
  两工况（DN100 / DN150）两段管时，第二个工况与这个 DN 不同 → 生成 `input_updates` → 编排器
  自动重算，把用户的 DN150 改成 DN100，两段都 verified，以 succeeded 收口，全程无人参与。
  系统 × 拓扑做笛卡尔积：一条边 + 两个系统生成两根 DN/坡度相同、都被同一个工况标 verified 的管。
  重复的 `(system, start, end)` 让 DesignPackage 抛裸 `duplicate segment_id` ValidationError。
- **拒绝后仍进 release_gate**：`approval → release_gate` 是无条件边。人工拒绝后 errors 变成
  `[MULTI_APPROVAL_REQUIRED, MULTI_APPROVAL_STALE]`，trace 出现 `export_attempt(approval_valid=false)`，
  `unapproved_export` 对每一次正常拒绝都报警；拒绝原因只在 LangGraph writes 表里；漂移 STALE 记两次。
- **非法 resume 值毒化会话**：`_strict_approval` 在 `interrupt()` 返回后才校验、不合法即抛。
  LangGraph 1.2.11 已把该值记进本任务的 resume 列表，异常让它随 ERROR 落盘；之后每次恢复第 0 个
  interrupt 先取到旧的非法值——实测再传合法值照样抛同一个 TypeError。此时 `get_state().next`
  为 `()`、`interrupts` 为 1，CLI `--resume` 只看 next，撞进"新运行"分支的 assert。
- **CLI "拒绝原因"处 Ctrl-C/EOF**：EOF 让 CLI 以退出码 2 崩出，Ctrl-C 原样抛出。

### 决策

8. **契约**：`TopologyEdge` 增加可选 `system` 与 `calc_case_id`（`extra="forbid"` 不变）。
   `calc_case_id` 指 `ProjectBrief.hydraulic_cases[].case_id`；重算后的活动工况 ID 为
   `<case_id>-<12 位 hex>`，设计 Agent 按这一派生规则解析，解析不到唯一一个即判不明。
   设计 envelope 与 multi_agent_p0 套件的 `schema_version` 升为 `p4.5-2026-10-01`。
9. **绑定规则**（任务书 §2.1"每个设计管段引用哪一个计算工况"）：边声明了就用声明的；未声明时
   只有恰好一个活动工况才自动绑定、恰好一个系统才自动归属。多工况或多系统而边未声明 → 管段
   `not_verified`（多系统时每个系统一根候选管，不做笛卡尔积式的 verified）、写 `unresolved_items`，
   设计 envelope 为 `missing_inputs`（转人工：缺的是人的声明，不是计算；没有任何活动工况支撑的
   `not_verified` 仍为 `blocked`）。
10. **DN 只有两个来源**：绑定工况自己的输入，或显式设计约束（`spatial_constraints` 的
    `diameter_mm`/`dn_mm` 优先于 `user_constraints` 里的 `DN…`，沿用既有优先级——结构化的管径修订
    不与自由文本里复述的 DN150 冲突）。单工况设计里唯一的显式 DN 是设计采用值，与工况输入不同才
    生成重算请求（§7.3，ma-p0-03 不变）；同源出现多个不同显式 DN → 转人工。多工况设计里项目级 DN
    归属不到某一个工况，只做一致性核对：每段的工况 DN 必须在显式值内、每个显式值必须有管段对应，
    否则转人工。**有歧义的管段永不生成会改写用户工况的重算请求**；坡度同样只取绑定工况的输入。
    单工况/单系统 brief 只有两处有意的行为变化：`user_constraints` 里的 DN 与工况输入不同时现在按
    §7.3 触发重算（此前工况 DN 排在它前面，等于被静默忽略）；同一来源给出多个不同 DN 时转人工
    （此前取第一个，或被工况 DN 盖过）。其余情况设计产物与修复前逐字节相同（multi_agent_p0 既有
    14 条全部如此）。
11. **冲突 brief 在 intake 结构化拒绝**：`project_brief_conflicts` 检查重复系统、重复 `case_id`、
    边引用未声明的系统/工况、两条边产生同一 `(system, start, end)` 管段；命中即
    `MULTI_INVALID_BRIEF` + 逐条原因，`status=missing_inputs`（与既有 intake 校验失败同口径），
    发 `run_finished`，不调用任何 Agent。直接调用设计 Agent 遇到冲突 brief 返回 `blocked` 空包，
    不再抛异常。同向重复才算重复；反向边（n2→n1 与 n1→n2）`segment_id` 不同，不判重复。
12. **审批之后改为条件边**：只有拿到有效批准才进 `release_gate`。拒绝与漂移在 approval 节点收口并
    发 `run_finished`；漂移只记一次 `MULTI_APPROVAL_STALE`；拒绝保持 `MULTI_APPROVAL_REQUIRED`
    （§10"产物已就绪但尚未人工批准"），不新增错误码。
13. **拒绝落库**：`ApprovalRecord(approved=False, reason=原因或 "rejected")`，绑定被拒绝的那个最终包
    哈希，`approved_at` 记决定时间、`expires_at=None`；`approval_resumed` 事件新增
    `approval_decision`（`approved`/`rejected`），trace 能看出这是一次人工拒绝。
    `FinalProjectPackage` 拒绝 `approved=False` 的记录。
14. **release_gate 不削弱**：6 项检查全部保留；只修正错误码选择——没有有效批准
    （`approval_exists=False`，例如审批被跳过）记 `MULTI_APPROVAL_REQUIRED`，不再因缺记录导致的
    `package_hash_matches=False` 误记成 STALE。
15. **非法 resume 值不抛异常**：校验拆为 `approval_decision_error`（合法返回 None、非法返回原因），
    approval 节点"非法就带 `error` 再 interrupt 一次"（与 PR #13 docgen 同一修法）：每次恢复本节点
    从头重跑、按序号重放此前收到的值，非法值落回原序号再次被判非法，新的合法值接在后面被取到。
    判挂起必须看 `interrupts`（此时 `next` 为 `()`）。实测被旧代码毒化的会话在新代码下传合法值即可
    恢复。
16. **CLI multi-agent**：`--resume` 判挂起以 interrupts 为准；没有待批准的请求时明确报错退出 2；
    审批请求带 `error` 时提示"上一次提交的审批决定无效，未被采纳"；两处提示的 Ctrl-C/EOF 都挂起、
    不提交任何决定，提示 `--resume`，退出码 0。
17. **评测口径**：`numeric_source_integrity` 按 §15.3"可追溯到输入或程序化结果"——未绑定工况的管段
    只能如实 `not_verified`，且 DN 只能是用户显式给出的值。ma-p0-09 改为真正"注入的未审批导出"：
    harness 用 `update_state(as_node="approval")` 跳过人工审批节点直奔发布门（不构造批准记录与事件），
    由生产 `release_gate` 拦下；普通人工拒绝改由新增的 ma-p0-18 覆盖。

### 残余

- 多工况设计里项目级 DN 约束一律只做一致性核对；要"整体升管径"必须改各工况输入，不会自动给多个
  工况重算。
- 用户若把某个 case_id 起成"另一个 case_id + `-<12 位 hex>`"的形态，声明解析可能命中两个 → 判不明转人工
  （不会错绑）。
- 审批过期（哈希一致但 `expires_at` 已过）在 release_gate 记 `MULTI_REVIEW_REJECTED` 的语义未处理；
  intake 的字段级校验失败仍不带 `MULTI_INVALID_BRIEF`（属"阶段失败不发错误码"，不在本次范围）。
- CLI 首个提示处非 y 的任何输入（含空行）仍按拒绝处理（docgen 在 PR #13 已改为重问，multi-agent 未跟进）。
- "重新挂起后 next 为 ()"是 LangGraph 1.2.11 的行为，升级 LangGraph 需复核判挂起口径。
