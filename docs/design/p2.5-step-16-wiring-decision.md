# P2.5 Review 修复决策记录：端到端接线收口

**日期**：2026-09-06
**状态**：已完成
**规格来源**：`docs/design/12-p2.5-production-governance.md`；P2.5 review 问题清单（一~七节）

> 本文档不含任何 API Key、用户原始输入或真实 trace 内容。攻击串均为合成样例。

## 0. 背景与目标

Step 11–15 已交付治理组件（ProviderGateway、GuardrailPipeline、AnswerCacheService、
检测器、观测），但 review 发现这些组件**尚未接入主业务链路**：护栏只在工具层，
RAG 图的输入/输出未过护栏；RequestContext 用固定 thread_id（`legacy-rag` /
`chat-agentic_loop` / `embedding` / `rerank`）；AnswerCacheService 未接进 RAG 图；
gateway 的 usage 事件未写 trace；TokenUsage 把"usage 缺失"写成 0。

本步把"组件已经写了"推进到"主业务链路真正经过治理"，不做无关重构、不删 legacy、
不放宽任何 fail-closed 规则。

## 1. 关键设计决策

### D1 统一接入点选在"图节点内"，而非 CLI 外层

review 要求「不要只在 CLI 外层加一层临时判断」。护栏与缓存因此做进
`graphs/rag.py`（legacy）与 `graphs/agent_rag.py`（agentic）的**图节点**里：

- 输入护栏在 `router`（legacy）/ `agent_loop`（agentic）——第一个节点，在检索、模型调用、
  缓存 lookup 之前；
- 输出护栏在 `finalize`（两条图）——在最终返回、写缓存、写 trace 之前；
- 缓存 lookup 在 `generate`（legacy provider 调用前）/ `agent_loop`（agentic 循环前）；
  缓存 store 在 `finalize`（引用/输出校验通过后）。

两条图的 `pipeline` / `request_context` / `cache_service` 参数均可选，缺省回落进程级
默认实例——仍经治理层，不存在"不传即绕过"的后门。

### D2 RequestContext 用真实会话/请求 thread_id

- **agentic CLI**（`AgenticSession`）：先创建 `thread_id`，再用它构造 `RequestContext`，
  经 `request_context_factory` 传入 `GovernedChatModel`，并传入 `ToolRegistry(principal=...)`
  与 `build_agentic_app(request_context=...)`。
- **legacy CLI**（`run_once`）：用本次 run 的稳定 `run_id` 构造 `RequestContext`，
  传给生成器 / embedding / rerank / 图。
- **harness/runner**：每条用例一个 `thread_id`，传给图与 `ToolRegistry`，并逐用例
  置位缓存的真实 chat model / generator 的 `request_context`。

`GovernedChatModel` 增加 `request_context_factory`（与固定 `request_context` 二选一）；
未显式提供时仍经 `default_gateway`，但主体未按会话隔离——仅向后兼容/测试路径。

### D3 缓存键新增 `category` 失效因子（跨分类隔离）

`AnswerCacheService` 原本的缓存键不含调用分类。legacy（`RAG_GENERATION`，可缓存）与
agentic（`AGENTIC_LOOP`，Step 13 明确不可缓存）的最终回答语义不同（单次结构化 JSON
vs 多轮工具调用），同 query/model/temperature/principal 会命中同一条目。为防**跨分类
互相命中**，`CacheKeyFactors` 新增 `category` 字段（默认 `RAG_GENERATION`），
`key_factors` / `lookup` / `store` / `invalidate` 均透传。

这是"新增失效维度必须改契约"的一次实例，有专项测试
（`test_category_participates_in_key`）。

### D4 agentic 缓存的"接入"语义 = 走服务但恒 fail-closed

`CallCategory.AGENTIC_LOOP ∉ CACHEABLE_CATEGORIES`（Step 13：多轮工具调用非幂等）。
因此 agentic 图**接入** AnswerCacheService 后，lookup 只会 MISS、store 恒 INELIGIBLE
（`REASON_CATEGORY`）。这不是"没接入"——代码路径与缓存事件都已接上，只是资格判定
按既有规则拒绝；将来若有独立评测解锁 agentic 缓存，只需改 `CACHEABLE_CATEGORIES`。

当前真实语料 `data/versions.json` 4 本规范全 `unknown`，legacy 的 store 也恒
INELIGIBLE（`REASON_SPEC_VERSION_UNKNOWN`）。**不得为提高命中率放宽版本校验**。

### D5 gateway 治理事件经 `on_usage` 写 trace

`JsonTraceRecorder` 新增 `record_provider_event`，按 `UsageRecord.result_status` 映射为
`usage` / `rate_limit` / `budget` / `breaker` / `failure` 事件；`usage_known=False` 时
token/cost 为 `None`（不写成 0）。`binding.default_gateway_with_sink(on_usage)` 复用
默认 gateway 的 config/stores（限流桶/预算账本跨会话累积、主体靠 principal_hash 分键），
只把 `on_usage` 换成当前 run 的 trace 回调——CLI/runner 据此把 usage/budget/rate-limit/
breaker/failure 事件按 trace schema 落盘，使 `budget_bypass` 检测器不再系统性误报。

### D6 检测器/聚合/告警接入可执行入口

新增 `scripts/governance_report.py`：读目录下 trace JSON → `tag_traces` →
`build_governance_report` → `evaluate_alerts` → `write_alert_events`。告警仍
`delivery="local_event_only"`——**不假装已发送 PagerDuty / Slack**，外部投递待单独决策。

### D7 TokenUsage 增加 `usage_known`，token/cost 改为可空

`domain.models.TokenUsage` 新增 `usage_known: bool = True`，token/cost 字段由
`int=0`/`float=0.0` 改为 `int|None=None`/`float|None=None`；`usage_known=False` 时
token/cost 必须为 `None`（model_validator fail-closed）。提供 `TokenUsage.unknown()`
与 `TokenUsage.known(...)` 两个构造器。JSON 兼容：`usage_known` 有默认值，旧数据仍可
解析；unknown 序列化为 `null` 而非 `0`。

`docgen/quality.py`（RealPolishTransport）、`harness/llm_judge.py`、`harness/runner.py`
的 TokenUsage 聚合均改为"缺失即 unknown / None，不求和、不写成 0"。

## 2. 明确拒绝的做法

| 做法 | 拒绝理由 |
| --- | --- |
| 在 CLI 外层加临时判断代替图内接入 | review 明确禁止；新路径会绕过 |
| 为 agentic 解锁缓存（放宽 `CACHEABLE_CATEGORIES`） | Step 13 明确 agentic 非幂等不可缓存；无独立评测 |
| 放宽版本校验以提高命中率 | 规格 §5 硬约束，`data/versions.json` 全 unknown 是刻意 fail-closed |
| 把 usage 缺失写成 0 token/0 成本 | 估算不得当账单；评测报告必须区分 known/unknown |
| 声称已发送 PagerDuty/Slack | 未接外部投递；`local_event_only` 是诚实边界 |

## 4. 已知限制（未收口，如实声明）

1. **缓存命中率仍结构性为 0**：`data/versions.json` 4 本规范全 `unknown`，store 恒
   INELIGIBLE。人工核实版本后自动解锁（相关测试 `test_real_corpus_store_is_rejected`
   会变红提示更新）。这是刻意的 fail-closed。
2. **agentic 缓存恒不可缓存**：`AGENTIC_LOOP ∉ CACHEABLE_CATEGORIES`（Step 13 决策）。
   接入只保证"走服务 + 事件落盘"，不产生命中。
3. **告警投递 `local_event_only`**：未接 PagerDuty/Slack，只写本地 JSONL。
4. **`check_memory_write` 未接 checkpointer**、**`materials/export.py` 未接路径校验**：
   沿用 Step 14/15 的已知缺口，本次不在范围内。
5. **harness/runner 的真实 embedding provider 仍共享固定主体**：eval 进程内所有用例
   共用一个 embedding provider（进程级主体）；rerank 与生成器已逐用例隔离。
6. **护栏是确定性正则**：必然存在未覆盖的改写变体，不得声称"能拦住任意注入"。
